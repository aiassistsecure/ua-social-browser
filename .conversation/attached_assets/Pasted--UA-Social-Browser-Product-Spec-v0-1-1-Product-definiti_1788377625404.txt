# UA Social Browser — Product Spec v0.1

## 1. Product definition

**UA Social Browser** is a Chromium fork for managing social media accounts from isolated browser workspaces, with AI-assisted writing and planning.

Each workspace has its own:

- User-Agent profile
- cookies and login sessions
- viewport and device settings
- language and timezone
- social accounts
- drafts and scheduled posts

The goal is to make social publishing feel like a native browser workflow without mixing identities or requiring users to keep ten tabs open.

## 2. Product principles

- **User-controlled:** AI suggests; the user reviews and publishes.
- **Isolated:** Account sessions and UA profiles never leak between workspaces.
- **Transparent:** The active UA profile is always visible.
- **Platform-respectful:** No CAPTCHA bypassing, stealth automation, scraping, fake engagement, or mass unsolicited posting.
- **Private by default:** Social content and API keys stay local/server-side and are never exposed to arbitrary websites.

## 3. MVP scope

### Chromium fork

Build a Chromium-based desktop browser with:

1. **UA workspaces**
   - Create, rename, duplicate, and delete workspaces.
   - Assign one UA profile to each workspace.
   - Launch each workspace in an isolated browser window.
   - Show the active profile in the browser toolbar.

2. **UA profile settings**
   - Profile name
   - User-Agent string
   - Platform: Windows, macOS, Linux, iOS, Android
   - Viewport width and height
   - Locale
   - Timezone
   - Optional Client Hints configuration

3. **Social sidebar**
   - Persistent sidebar inside the browser.
   - Dashboard
   - Composer
   - Drafts
   - Content calendar
   - Connected accounts
   - AI assistant
   - Current workspace and UA profile indicator

4. **AI-assisted composer**
   - Generate post ideas.
   - Rewrite text.
   - Change tone.
   - Shorten or expand copy.
   - Generate hashtags.
   - Create platform-specific variants.
   - Suggest calls to action.
   - Explain why a suggestion may work.
   - Save generated results as drafts.

5. **Human-reviewed publishing**
   - Save draft.
   - Schedule draft.
   - Open the selected social platform with the content prepared.
   - Require explicit user confirmation before publishing.
   - Official platform APIs may be added later through adapters.

## 4. Core user flows

### Create a workspace

1. User clicks **New Workspace**.
2. Enters a name, such as `Brand LinkedIn`.
3. Selects or creates a UA profile.
4. Chooses viewport, locale, and timezone.
5. Browser opens a new isolated window.
6. User signs into the relevant social account.
7. Workspace persists its cookies and settings separately.

### Create an AI-assisted post

1. User opens the sidebar Composer.
2. Selects:
   - Platform
   - Workspace
   - Content goal
   - Tone
   - Audience
   - Desired length
3. User enters a rough idea or source text.
4. AI returns several suggestions.
5. User edits or combines suggestions.
6. User previews the post.
7. User saves, schedules, or opens the platform for manual publishing.

### Switch identities safely

1. User selects another workspace.
2. Current workspace remains isolated.
3. New workspace opens with its own cookies, UA, viewport, and settings.
4. Sidebar clearly displays the active workspace.
5. The browser never silently changes a workspace while the user is composing.

## 5. AI integration

The AI integration must run through the application backend, never directly from browser-rendered JavaScript.

The published AiAssist OpenAPI contract describes an OpenAI-compatible `POST /v1/chat/completions` endpoint using a Bearer API key, plus `GET /v1/models` for available models. It also documents optional provider and agent headers.

### Backend endpoints

```text
POST /api/ai/suggest
GET  /api/ai/models
GET  /api/ai/usage
```

### `POST /api/ai/suggest`

Request:

```json
{
  "workspaceId": "workspace_123",
  "platform": "linkedin",
  "task": "rewrite",
  "tone": "confident and useful",
  "audience": "early-stage founders",
  "sourceText": "Raw user-provided content",
  "constraints": {
    "maxCharacters": 1300,
    "includeHashtags": true,
    "numberOfSuggestions": 3
  }
}
```

Response:

```json
{
  "suggestions": [
    {
      "text": "Generated post text",
      "rationale": "Why this version may work",
      "characterCount": 412
    }
  ],
  "model": "selected-model",
  "usage": {
    "inputTokens": 120,
    "outputTokens": 280
  }
}
```

### AiAssist adapter

The backend should:

- Store the AiAssist key in a server-side secret.
- Send requests to `/v1/chat/completions`.
- Use `/v1/models` to populate the model selector.
- Support optional provider and agent configuration.
- Record token usage and estimated cost.
- Return friendly errors for invalid keys, rate limits, and unavailable models.
- Never log source content or API keys by default.

The browser UI should not know the API key, even if a user opens DevTools on the sidebar.

## 6. Chromium architecture

### New browser concepts

```text
UAWorkspace
 ├── workspaceId
 ├── displayName
 ├── profileDirectory
 ├── uaProfileId
 ├── socialAccounts[]
 ├── locale
 ├── timezone
 └── viewport
```

```text
UAProfile
 ├── profileId
 ├── name
 ├── userAgentString
 ├── platform
 ├── viewportWidth
 ├── viewportHeight
 ├── locale
 ├── timezone
 └── clientHints
```

### Chromium changes

The fork should add:

- A workspace manager.
- Isolated profile directories.
- Workspace-specific browser windows.
- UA configuration at the network-context level.
- User-Agent Client Hints configuration where supported.
- Toolbar indicator for active workspace and UA profile.
- Sidebar integration through a privileged internal browser page.
- IPC between the Chromium UI and the social manager.
- Permission boundaries preventing ordinary webpages from accessing workspace secrets or AI configuration.

### Recommended implementation order

1. Workspace creation and isolated profile directories.
2. One UA profile per workspace.
3. Toolbar indicator.
4. Sidebar shell.
5. AI backend and composer.
6. Draft persistence.
7. Calendar and scheduling.
8. Social platform adapters.

Per-tab UA switching should not be part of the first implementation. Workspace- or window-level switching is substantially safer and more predictable.

## 9. Security requirements

- No social credentials stored in the application database.
- Cookies remain in Chromium’s encrypted profile storage.
- AI keys exist only in server-side environment secrets.
- Sidebar runs in a privileged isolated context.
- External pages cannot access the sidebar’s local storage or IPC methods.
- Every workspace has a separate browser profile directory.
- Workspace switching requires a visible UI action.
- Publish actions require explicit confirmation.
- Sensitive content is excluded from logs.
- Exported workspace data must exclude cookies and credentials by default.

## 10. Non-goals for v0.1

Do not build:

- CAPTCHA bypassing
- Anti-detection or stealth fingerprinting
- Automated likes, follows, comments, or DMs
- Bulk account creation
- Scraping of social platforms
- Automatic publishing without user confirmation
- Full per-tab UA emulation
- Mobile app versions
- Team permissions
- Billing
- Ten social network integrations at once

## 11. Acceptance criteria

The MVP is successful when:

1. The Chromium fork launches successfully.
2. A user can create two isolated workspaces.
3. Each workspace can use a different UA profile.
4. A UA test page sees the configured User-Agent.
5. Cookies from one workspace are not visible in another.
6. The active workspace is always visible in the browser UI.
7. The sidebar can create and save a draft.
8. The sidebar can request AI suggestions through the backend.
9. The AiAssist key never reaches the renderer or external webpage.
10. A user can schedule a draft locally.
11. The product requires confirmation before opening a publish flow.
12. AI usage and errors are visible to the user.

## 12. Budget reality

With $12 in Replit credits, the first milestone should be a **vertical proof of concept**, not a signed, production-distributed Chromium release:

- Chromium fork compiles or launches from a development build.
- Two isolated UA workspaces work.
- Sidebar opens.
- AiAssist request succeeds.
- One draft flow works end to end.

A full Chromium fork with automatic updates, code signing, installers, crash reporting, security patching, and multi-platform builds is a later project. The spec should target that architecture now, but the first implementation should prove the core browser behavior before spending credits on distribution infrastructure.
